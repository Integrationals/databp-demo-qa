Step 6. The hashed step at the end of each staging model, after the reference architecture's stg_harbor__hubspot_contacts (D-1, D-5, G-1 to G-3). The usage report's, in full:

with landed as (
    -- the model's current select, unchanged
),

hashed as (
    select
        {{ dbt_utils.generate_surrogate_key(["cast(tenant_id as varchar)", "cast(declaration_id as varchar)"]) }} as declaration_hkey,
        {{ dbt_utils.generate_surrogate_key([
            "tenant_id", "declaration_id", "customer_id", "product_code",
            "usage_month", "declared_units", "declared_at", "is_deleted"
        ]) }} as declaration_hdiff,
        {{ get_business_key_source("cast(tenant_id as varchar) || '|' || cast(declaration_id as varchar)", "USAGE", "|", "USAGE_DECLARATION") }} as declaration_code,
        {{ get_business_key_source("cast(tenant_id as varchar)", "DATABP", "|", "CLIENT") }} as client_code,
        {{ get_business_key_source("cast(tenant_id as varchar) || '|' || cast(customer_id as varchar)", "DATABP", "|", "CUSTOMER") }} as subscriber_code,
        {{ get_business_key_source("cast(tenant_id as varchar) || '|' || product_code", "DATABP", "|", "PRODUCT") }} as product_key_code,
        landed.*,
        'USAGE' as record_source,
        '{{ run_started_at }}'::timestamp as load_ts_utc
    from landed
)

select * from hashed

Each model's columns. The code's parts are issuer, table and natural id; record_source is DATABP for the DataBP models, SFDC for Salesforce's and USAGE for the usage report. Every hdiff covers the columns named and is_deleted, and leaves out landed_at, changed_at and updated_at (G-3).

Verification queries

The unit tests' literals (G-6), written out from generate_surrogate_key's form rather than called through it: each part cast to text, a null replaced by dbt_utils' marker, the parts joined by a hyphen, then md5. For the usage report's four rows:

select
    md5('3' || '-' || '2')                                                                   as h1,
    md5('3-2-23-OPTIONS-2026-10-01-12-2026-11-05 00:00:00.000-false')                        as d1,
    md5('3-2-23-OPTIONS-2026-10-01-15-2026-11-05 00:00:00.000-false')                        as d2,
    md5('3-2-23-OPTIONS-2026-10-01-12-2026-11-05 00:00:00.000-true')                         as d3

The text of a date, a timestamp and a boolean cast in Snowflake is read first, with a select of each cast, so that the strings above match what the compiled model produces; the compiled SQL of the model is read beside them, which also confirms generate_surrogate_key's form, as design section 4 requires.

The key reconciliation (D-4, test plan layer 6), run for each silver and gold table, Development's schema against Production's, with the same key columns as B-1 and B-2:

select 'usage_report' as t,
       (select count(*) from DATABP_LAB.DBT_CLAUDE_SILVER.USAGE_REPORT) as dev_rows,
       (select count(*) from DATABP_LAB.DATABP_SILVER.USAGE_REPORT)     as prod_rows,
       (select hash_agg(usage_report_hk, client_hk, subscriber_hk, product_hk) from DATABP_LAB.DBT_CLAUDE_SILVER.USAGE_REPORT) as dev_hash,
       (select hash_agg(usage_report_hk, client_hk, subscriber_hk, product_hk) from DATABP_LAB.DATABP_SILVER.USAGE_REPORT)     as prod_hash

Equal rows and equal hashes in every table; a difference stops the cycle, and the rows that differ are found with a full outer join on the keys. Customer 23's key read in DBT_CLAUDE_SILVER.SUBSCRIBER must be 6e7a1ee374a6187c721a8a2ea0017019 (B-4).

8. Decisions recorded in this guide

ID Weed-level choice Rationale
G-1 The product's code is named product_key_code, since product_code is DataBP's natural column D-5 asks for _code; the natural name stays
G-2 A row that names another entity carries that entity's code: client_code from the tenant id, subscriber_code, product_key_code, invoice_code on the invoice item Silver makes each key from a code staging created (design 6.5)
G-3 The hdiff covers every attribute and is_deleted, and leaves out landed_at, changed_at and the source's updated_at The reference architecture's hdiff leaves out last_modified_date; a reload is not a change
G-4 Each silver key is wrapped: when its code is null, the key is null md5 of a null is null today, but generate_surrogate_key of a null is not; values must not move (D-4)
G-5 A silver row joined from several staging rows carries its main row's hdiff change_hash is read by nothing; the main row is what the key names
G-6 The unit tests' expected hkey and hdiff are literals computed in Snowflake with md5 over the columns written out, not with the macro A wrong column list fails the test
G-7 If this project's dbt cannot unit test or data test an ephemeral model, the build stops and C-2 returns to Ray D-6 requires it proven in Development; no fallback is chosen here

9. Rollback

Revert the merge commit on databp-dbt main and run the Production job by hand. Staging returns to views, silver to md5 of business_key; every key value is the same either way, so gold, the metrics and the site are untouched throughout.
