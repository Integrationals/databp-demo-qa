How the reconciliation was implemented in dbt

One source table, the usage report, followed from landing to the figure the app shows.

The reconciliation answers one question for a data provider: for each subscriber, product and month, do the license, the entitlement, the usage report and the invoice agree, and what does each disagreement cost? This page shows how it was built by following one source table, the usage report, from the moment it lands in Snowflake to the figure the app shows, with one subscriber's October report traced the whole way: Customer 23, product Options.

The data comes from three source systems: DataBP, which issues every subscriber and product its identifier; Salesforce, which holds the licenses; and the usage-reporting system, where subscribers report the units they used. The project is a dbt project, Integrationals/databp-dbt, built on the medallion architecture and on our reference architecture's patterns for keys and data integration. dbt builds the warehouse in layers, each a folder of models, a model being one SQL file that dbt turns into a view or a table: staging, silver, gold, and on top of gold the Semantic Layer, where the metrics are defined. Each layer reads only the one below it.

The code below is quoted from the project at commit 553f290; every row and figure was read from Production on 2026-11-23, after the Production job's run [id].

1. Landing: the report as it arrives

The usage-reporting system keeps a subscriber's monthly count of units used in a SQL Server table, USAGE_DECLARATION. Snowflake Openflow, the connector, copies it into Snowflake as DATABP_LAB.DATABP_USAGE_DBO.USAGE_DECLARATION and adds three columns of its own: when it inserted the row, when it last updated it, and whether the source deleted it.

dbt does not change landed tables; it declares them as sources, so models can read them by name and dbt can test them. A not-null test on the report's id runs on every build (descriptions left out):

  - name: databp_usage
    database: DATABP_LAB
    schema: DATABP_USAGE_DBO
    tables:
      - name: usage_declaration
        identifier: USAGE_DECLARATION
        columns:
          - name: declaration_id
            data_tests: [not_null]

2. Staging: the same rows, with their keys

A staging model reads one landed table, renames the connector's columns into the project's terms and turns its delete marker into a flag, is_deleted. Nothing is filtered or joined here, so staging always shows exactly what landed. It then creates the row's keys, so that every layer above uses the same ones:

  • the code, the row's business key in its issuer's namespace: issuer, table and natural id joined by bars, such as USAGE|USAGE_DECLARATION|3|2;
  • the hkey, the row's identity, a hash of its natural id;
  • the hdiff, the row's change key, a hash of every attribute whose change matters, so a changed row can be found by comparing one value;
  • record_source, the issuer, and load_ts_utc, the run's start.

A row that names another entity also carries that entity's code, in DataBP's namespace, because DataBP issues the identifiers: the usage report carries its data provider's code, DATABP|CLIENT|3, its subscriber's, DATABP|CUSTOMER|3|23, and its product's, DATABP|PRODUCT|3|OPTIONS.

The hashes come from dbt_utils.generate_surrogate_key, the standard dbt package's macro; the codes from one macro of the project, get_business_key_source, so every code is built the same way. Staging models are ephemeral, set once for the whole folder in the project's configuration: dbt compiles each into the models that read it rather than building a view, so staging adds no objects to the warehouse.

models/staging/stg_databp__usage_usage_declaration.sql:

with landed as (
    select
        tenant_id,
        declaration_id,
        customer_id,
        product_code,
        usage_month,
        declared_units,
        declared_at,
        coalesce(_snowflake_deleted, false)      as is_deleted,
        _snowflake_inserted_at                   as landed_at,
        _snowflake_updated_at                    as changed_at
    from {{ source('databp_usage', 'usage_declaration') }}
),

hashed as (
    select
        {{ dbt_utils.generate_surrogate_key(["cast(tenant_id as varchar)", "cast(declaration_id as varchar)"]) }} as declaration_hkey,
        {{ dbt_utils.generate_surrogate_key([
            "tenant_id",
            "declaration_id",
            "customer_id",
            "product_code",
            "usage_month",
            "declared_units",
            "declared_at",
            "is_deleted"
        ]) }} as declaration_hdiff,
        {{ get_business_key_source("cast(tenant_id as varchar) || '|' || cast(declaration_id as varchar)", "USAGE", "|", "USAGE_DECLARATION") }} as declaration_code,
        {{ get_business_key_source("cast(tenant_id as varchar)", "DATABP", "|", "CLIENT") }} as client_code,
        {{ get_business_key_source("cast(tenant_id as varchar) || '|' || cast(customer_id as varchar)", "DATABP", "|", "CUSTOMER") }} as subscriber_code,
        {{ get_business_key_source("cast(tenant_id as varchar) || '|' || cast(product_code as varchar)", "DATABP", "|", "PRODUCT") }} as product_key_code,
        landed.*,
        'USAGE' as record_source,
        '{{ run_started_at }}'::timestamp as load_ts_utc
    from landed
)

select * from hashed

{{ source(...) }} is how dbt names the landed table declared in step 1; with landed as (...) names a query, a common table expression, that the next one selects from. The hdiff leaves out the load times, so reloading an unchanged row does not count as a change.

3. Silver: one view of each subscriber, then the report

Silver is where data is matched, merged, conformed and cleansed into one view of the business's key entities. It holds two sets of tables. The entities, the subscriber and the product, are merged across the three systems, because all three name them. The transaction tables, the license, the entitlement, the usage report and the invoice item, each stay one table per source, keyed to the merged entities; they meet only in gold.

Resolving the subscriber

Each system knows Customer 23 its own way. DataBP holds the customer, with its name and email. Salesforce holds the same customer under its own id, and carries DataBP's tenant and customer id on it, in the fields Tenant__c and Subscriber_Id__c, so its staging model creates DataBP's subscriber code beside its own. The usage system names the customer by DataBP's tenant and customer id on every report.

So every system's row carries DataBP's subscriber code, and silver's subscriber model resolves on it, following the reference architecture's resolution pattern in steps, each a common table expression inside the model: the source rows, every system's subscriber rows stacked into one set; the match, one row per DataBP code with a count of each system's rows; then the merged subscriber. A code that DataBP itself does not hold is not dropped: it keeps its row and is counted as created. The key is generate_surrogate_key over the DataBP code, so any table that carries the code computes the same key without a join.

models/silver/subscriber.sql, its steps (the attributes taken from each system left out):

source_rows as (
    select 'DATABP' as source_system, subscriber_code, client_code from databp
    union all
    select 'SALESFORCE', subscriber_code, client_code from salesforce
    union all
    select 'USAGE', subscriber_code, client_code from usage_reported
),

matched as (
    select
        subscriber_code,
        any_value(client_code)                           as client_code,
        count_if(source_system = 'DATABP')             as databp_source_rows,
        count_if(source_system = 'SALESFORCE')         as salesforce_source_rows,
        count_if(source_system = 'USAGE')              as usage_source_rows
    from source_rows
    where subscriber_code is not null
    group by subscriber_code
)

select
    {{ dbt_utils.generate_surrogate_key(["matched.subscriber_code"]) }}  as subscriber_hk,
    ...
    matched.databp_source_rows = 0                                        as is_created,
    coalesce(salesforce_first.account_name <> databp.customer_name, false) as name_differs,
    ...
from matched
left join databp           on databp.subscriber_code = matched.subscriber_code
left join salesforce_first on salesforce_first.subscriber_code = matched.subscriber_code
left join usage_reported   on usage_reported.subscriber_code = matched.subscriber_code

A union all stacks the three systems' rows into one set; count_if counts the rows that meet its condition; a left join keeps every code, whether or not that system has a row for it. databp, salesforce and usage_reported are the model's first steps: each system's staging rows that are not deleted, the usage reports reduced to one row per subscriber with the first and last month reported; salesforce_first keeps one Salesforce row per code.

The product is resolved the same way, on DataBP's product code, which Salesforce's products and the usage reports also carry.

The usage report

The usage report is a transaction table, so silver keeps it as one table, cleaned. A subscriber may restate a month by sending a second report for the same product and month. Counting both would double the units, so silver keeps one: the latest declared, and when two share a time, the one filed last. Deleted rows are dropped. Each report hashes the codes staging gave it into its keys, so its subscriber key is the merged subscriber's without a join.

models/silver/usage_report.sql:

with report as (
    select * from {{ ref('stg_databp__usage_usage_declaration') }} where not is_deleted
    qualify row_number() over (
        partition by tenant_id, customer_id, product_code, usage_month
        order by declared_at desc, declaration_id desc
    ) = 1
)

select
    case when declaration_code is not null then {{ dbt_utils.generate_surrogate_key(["declaration_code"]) }} end as usage_report_hk,
    case when client_code is not null then {{ dbt_utils.generate_surrogate_key(["client_code"]) }} end as client_hk,
    case when subscriber_code is not null then {{ dbt_utils.generate_surrogate_key(["subscriber_code"]) }} end as subscriber_hk,
    case when product_key_code is not null then {{ dbt_utils.generate_surrogate_key(["product_key_code"]) }} end as product_hk,
    declaration_id,
    usage_month,
    declared_units                                                                          as reported_units,
    declared_at,
    declaration_hdiff as usage_report_hdiff,
    landed_at
from report

{{ ref(...) }} reads another model and tells dbt to build that one first; qualify keeps only the row the window function ranks first; each key is made only when its code is present, so a missing code leaves the key empty rather than hashing nothing.

4. Gold: the report beside the license, priced

Gold is what the metrics read. Its central table, subscriber_product_month_metric, holds one row per subscriber, product and month that has a row in any of the four transaction tables. Each is summed to that grain; the grain is the union of their keys; each joins to it, and one with no row counts as zero units, so a subscriber who reported usage with no license shows every reported unit as beyond the license.

Each row carries its own results, so one subscriber's excess is never netted against another's shortfall. Unbilled usage is the units reported beyond the license, priced at the product's unit price:

coalesce(license.licensed_units, 0)     as licensed_units,
coalesce(report.reported_units, 0)      as reported_units,
...
greatest(reported_units - licensed_units, 0)                    as units_reported_beyond_licensed,
greatest(reported_units - licensed_units, 0) * unit_price       as unbilled_amount

The unit test gives three subscribers a license of 10 at $50 a unit and reports of 12, 10 and 8, and expects $100 unbilled for the first and nothing for the other two: a shortfall never becomes a negative amount.

5. The Semantic Layer: the figure the app shows

Totals are not stored. The metric is defined once, in YAML beside the gold table, as a sum of each row's unbilled amount; the Semantic Layer computes it for any month, subscriber or product asked, so the Hex app and Morgan, the site's agent, read the same number:

- name: unbilled_revenue
  description: "Units reported beyond licensed times the product's unit price: usage the provider did not bill"
  label: Unbilled revenue
  type: simple
  agg: sum
  expr: unbilled_amount
  fill_nulls_with: 0

Asked of the Semantic Layer by month, unbilled revenue for October 2026 is $1,410, and Morgan gives the same figure. Customer 23's $80 is one of its eight rows: $850 for Customer 43, $100 each for Customers 83 and 123, $80 each for Customers 23, 63, 103 and 143, and $40 for Customer 303. The merged subscriber also gives the metrics two new ways to slice: whether the subscriber is in Salesforce, and whether it reports usage.

How the whole is proven

The source data was generated with every disagreement planted on purpose and written to an answer key, loaded into dbt as a seed, a CSV file dbt turns into a table. One test compares every row of gold with the answer key and returns any row that differs; it passes only when the reconciliation finds exactly the planted rows, no more and no fewer. dbt runs it, with every unit and data test, on each build. When the merged subscriber and product went into Production, every table in silver and gold was compared with a copy taken just before: the same rows, on every column they had before.

What the tests do not prove

That the answer key covers every case real data will bring; that a provider's real usage reports are complete. The first is bounded by the cases planted; the second is what the reconciliation is for.

What the POC leaves out

The reference architecture adds two layers this POC does not include: a storage layer that keeps every version of every source row, so any past state can be rebuilt, and an integration layer on the Universal Data Model, where parties, products and agreements from every source are integrated into one enterprise model. Both are premium features, not included in the POC.
