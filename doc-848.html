1. Purpose

databp-dbt is the POC Bin Luo, DataBP's CTO, judges our craft by, and its keys are built its own way: md5 of a home-made macro, created in silver, with names of our own. The reference architecture creates them in staging with dbt_utils.generate_surrogate_key and its business key macro, and every guide that builds on it follows that shape. This change brings databp-dbt's staging and keys to the reference architecture's form, on the medallion as it is, without its storage layer or UDM, which stay premium features outside the free POC. It is written for Ray, who decides, and for the session that builds it.

3. Concept

Today each of databp-dbt's 12 staging views renames a landed table's columns and turns the connector's delete marker into a flag, and creates no key. Silver then makes every key: md5 of the project's macro business_key, issuer, table and natural id joined by bars, named for its entity with _hk, beside a change_hash of a few columns. The reference architecture does it in staging: each staging model creates a code, the issuer, table and natural id, with its macro get_business_key_source; an hkey, identifying the row, and an hdiff, detecting its change, both with dbt_utils.generate_surrogate_key; and stamps record_source and load_ts_utc. The next layer makes its id from the code, again with generate_surrogate_key. This change gives databp-dbt that shape. The code is the same string business_key makes today, and generate_surrogate_key of one string that is not null is the md5 of that string, so every key value stays as it is.

6.3 Domain content

A staging model reads its landed table, renames its columns, turns the connector's delete marker into is_deleted, and ends with a hashed step that adds the code, the hkey, the hdiff, record_source and load_ts_utc, as the reference architecture's staging models end. Silver reads the code and makes the row's key with generate_surrogate_key; a key to another entity, such as a usage report's subscriber, is made the same way from the code that entity would carry.

6.4 Instance models

Customer 23 in staging after the change: code DATABP|CUSTOMER|3|23; hkey the surrogate key of 3 and 23; hdiff over the attributes that matter. In silver: the key generate_surrogate_key of the code, 6e7a1ee374a6187c721a8a2ea0017019, as today.

6.5 Worked examples

Customer 23's usage report for October: staging gives its own code, USAGE|USAGE_DECLARATION|3|2, and the subscriber's code it carries, DATABP|CUSTOMER|3|23; silver keys the report by the first and points to the subscriber by the second, the same subscriber key as DataBP's own row and as the Salesforce license's, so gold joins them as it does today.
