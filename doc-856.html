0. Target ERD

NA: no new entity and no new table; silver's subscriber and product gain columns from Salesforce and the usage system, and the resolution runs as CTEs inside them (section 6.1).

1. Purpose

Silver should be what the industry calls silver: data matched, merged, conformed and cleansed into one view of the key business entities. Ours conforms keys but merges nothing, so the page task 798 writes for Bin Luo, DataBP's CTO, could not show integration where the industry expects it. This change merges the two entities all three systems name, the subscriber and the product, by the steps of the reference architecture's resolution, on the codes staging now creates (task 2290), and leaves the transaction tables, the license line, entitlement, usage report and invoice item, as source-aligned tables. It is written for Ray, who decides, and for the session that builds it.

3. Concept

Today silver's subscriber and product come from DataBP alone; Salesforce's customer and product appear only as DataBP keys inside the license line. After task 2290 every staging row carries the codes of the entities it names: Salesforce's customer carries DataBP's subscriber code, Product2 and the usage report carry DataBP's product code. This change resolves each system's subscriber and product onto DataBP's, the anchor, by the steps of the reference architecture's resolution view: each system's source row is matched to the anchor by the code it carries, the matches are counted, a source row that matches nothing is created and counted, and a source row that matches more than once is surfaced. The reference keys a created source row by its own code because its systems carry no anchor identifier; ours all carry DataBP's, so every key, matched or created, is generate_surrogate_key of the carried DataBP code. That makes the resolution's key the same value the transaction tables already make from their own carried codes, so the resolution needs no table: it runs as CTEs inside subscriber and product, and its result is one row per key, DataBP's values leading and every other system's kept beside them. History is not kept here: the reference architecture keeps it in its storage layer (Ray, 2026-11-23 00:44 ET), outside the POC.

6.3 Domain content

The subscriber model's first CTE unions three sets of source rows, each a system's identifier with the DataBP subscriber_code it carries: DataBP's customers, whose code is their own; Salesforce's customers; and the usage system's distinct subscribers. The next joins each source row to DataBP's customers on that code and counts each system's source rows per code. The last builds one row per code: DataBP's attributes where the anchor exists, a created flag where it does not, Salesforce's and the usage system's columns and counts, and the key, generate_surrogate_key of the code. The product model works the same way.
